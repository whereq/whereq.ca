# WhereQ App Hub v1.7.0 — map-credentials

> The `/map` feature now actually loads Google Maps with the key you
> saved — and the map finally draws its imagery instead of an empty
> grey box.

## What's in this release

- **The map loads with your own API key.** The map page used to read the
  *map ID* field as the API key, so a key saved in the "API Key" field
  was never used: the Maps JavaScript API was requested without a key
  and every call came back as `ApiProjectMapError`. The API key and the
  map ID are now two separate settings, and a key that was saved in the
  map ID field is recovered automatically.
- **The API key is read at the right moment.** The Maps JavaScript API
  is loaded exactly once, when the map page first renders. A key that
  arrived a moment later was already too late, so the key is now read
  while the page renders. The same applies to the map ID: it is read
  before the map is built, which is what lets Google draw advanced
  markers on it.
- **A clear prompt instead of a broken map.** With no API key saved, the
  map page now shows a short message and an "Open settings" button
  rather than a map covered by Google's "This page can't load Google
  Maps correctly" overlay.
- **The map now draws its imagery.** The site served
  `Cross-Origin-Embedder-Policy: require-corp`, which refuses
  cross-origin resources that do not opt in with a resource-policy
  header — and Google's map imagery does not. The map rendered empty
  for every user whose key actually worked. The site now serves
  `credentialless`, which keeps cross-origin isolation (so the video
  engine and the background remover are unaffected) and lets the
  imagery through.
- **Settings panel corrections.** Saving no longer stores the
  placeholder text as the real credential; "Revert" restores the map
  settings instead of an unrelated storage entry; and changing the key
  or the map ID now says plainly that a reload is needed, because the
  Maps API is only loaded once.

## Notes

- **Bring your own key.** The map feature is BYOK: the key lives in your
  browser's local storage and is never sent to WhereQ.
- **Give the key the whole site, not just the home page.** Google compares
  the path of the page that was loaded, so a key restricted to
  `https://www.whereq.ca` alone is refused on `/map`, `/lab` and every
  other route with "This IP, site or mobile application is not
  authorized to use this API key". To allow the whole site, list
  `https://*.whereq.ca/*` and `https://www.whereq.ca/*` (plus
  `https://whereq.ca/*`, and `http://localhost:4173/*` if you work on it
  locally). A path wildcard that follows a literal segment — for example
  `https://*.whereq.ca/map/*` — does **not** cover `/map` itself: it
  needs at least one more segment after the slash.
- **The address-search fallback needs an IP-restricted key.** Google's
  geocoding service does not accept keys that are restricted to web
  addresses; the place autocomplete is the path that works in a
  browser.
- The video engine, the background remover and the in-browser code
  formatter were re-tested under the new header: the video engine still
  cuts and exports valid video, and the code formatter still loads its
  runtime from the CDN.
