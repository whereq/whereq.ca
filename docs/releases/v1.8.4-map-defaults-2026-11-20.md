# WhereQ App Hub v1.8.4 — map-defaults

> The map used to ask every visitor for their own Google Maps key before it
> would load anything. Now the deployment carries its own key and map ID, and
> the map just works. Your own key still wins if you set one.

## What's in this release

- **The map now works straight away for a new visitor.** The deployment
  ships its own Google Maps API key and map ID. Open `/map` and the map
  loads — no key prompt, no settings panel in your face. Previously every
  visitor had to create a Google Cloud project and enter a key before the
  map would appear at all.
- **A key you saved yourself still takes priority.** The settings panel is
  unchanged as the override: a key stored in your browser always wins over
  the shared one, and you can switch back and forth at any time.
- **The settings panel now says which key is in use.** It tells you when
  the map is running on the shared WhereQ key, and it no longer copies that
  shared key into your browser's storage when you press Save — so a later
  rotation of the site key reaches you too.
- **The shared key is kept in its own Google Cloud project**, separate from
  the other WhereQ apps, so its usage and its bill are attributed to whereq.ca
  on their own.

## Notes

- **The key in the page is not a secret.** Any website that uses a Google
  Maps key sends it to the browser, and this one does too. What protects it
  is the restriction set on it in Google's console — it is allowed to call
  only the Maps APIs this site uses, and only from this site's domain — plus
  a billing alert on the project. That is the normal arrangement for every
  browser map, not a shortcut.
- **The values are read when the site is built**, not when the page opens, so
  a change to them needs a fresh deployment before it reaches the browser.
- **How this was checked:** against a local production build, the fallback
  path and the saved-key path produced an identical map (same tiles, same
  DOM, no console errors beyond the known headless renderer note), the place
  search returned live predictions through the fallback, a visitor's own key
  was confirmed to override the deployment's, and saving the settings panel
  was confirmed to store empty strings rather than a copy of the shared key.
